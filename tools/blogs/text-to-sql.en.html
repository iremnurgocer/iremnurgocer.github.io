1. Promise and reality

The promise of Text-to-SQL is simple: business units should not have to wait in the developer queue to get at data, but ask their question in their own words. The reality is this: a language model is quite good at producing SQL that is syntactically correct but semantically wrong.

The answer to "How many customers did we win last month?" depends on the definitions of "customer" and "win". Are cancellations counted? Are trial accounts included? The model cannot know this; if you do not tell it, it guesses, and the guess looks plausible.

The real issue is not security but meaning

You solve security with engineering: a read-only role, an allowlist, validation. To solve meaning you have to explain the schema to the model - just giving it table names is not enough.

2. Providing schema context

Adding the entire database schema to the prompt is both expensive and ineffective. A three-step approach gives much better results:

  • Schema selection: retrieve the tables relevant to the question. Building a search index by embedding table and column descriptions is the single most effective improvement.
  • Enriched definitions: next to each column name, write what it means, its unit and example values.
  • Example queries: 10-20 questions the organisation asks often, with their correct SQL, are the best way to teach the model. 
-- Modele verilen şema bağlamı: ad değil, anlam
-- tablo: satislar - onaylanmış satış kalemleri (iptaller haric)
--   tarih         DATE    -- satışın onaylandığı gün
--   urun_kodu     TEXT    -- örn. 'AX-1042'
--   adet          INT     -- satılan birim
--   net_tutar     NUMERIC -- KDV haric, TRY
--   musteri_id    INT     -- musteriler.id
-- NOT: iade edilen kalemler bu tabloda yer almaz; iadeler tablosuna bakın.

Notes like that last line directly prevent the model's most common mistakes. Writing down the "everyone knows" knowledge in the data team's heads is the most valuable part of this work.

3. The pipeline: generate, validate, execute

SQL generated by the model should not go straight to the database. The layer in between does the following:

StageCheck
ParsingIs it valid SQL? Is it a single statement (no semicolon chaining)?
Statement typeOnly SELECT / WITH. INSERT, UPDATE, DELETE and DDL are rejected.
Object allowlistOnly tables and views that are permitted to be exposed.
Row-level permissionsRows the user may not see are added to the query as a filter.
LimitsMandatory LIMIT, query timeout, cost estimate.
ExecutionRead-only connection, separate user, separate resource pool.
 
IZINLI_TABLOLAR = {"satislar", "musteriler", "urunler"}

def dogrula(sql, kullanici):
    agac = sqlglot.parse(sql)
    if len(agac) != 1:
        raise Gecersiz("tek ifade bekleniyor")

    ifade = agac[0]
    if not isinstance(ifade, (exp.Select, exp.With)):
        raise Gecersiz("yalnızca okuma sorgularına izin var")

    kullanilan = {t.name for t in ifade.find_all(exp.Table)}
    if not kullanilan <= IZINLI_TABLOLAR:
        raise Gecersiz(f"izinsiz nesne: {kullanilan - IZINLI_TABLOLAR}")

    ifade = satir_yetkisi_uygula(ifade, kullanici)   # ör. sirket_id = :sirket
    return ifade.limit(1000).sql()
An allowlist is safer than a blocklist

Writing a blocklist "so that DROP does not get through" is a filter waiting to be bypassed. Define not what is forbidden, but what is allowed.

4. Security on the database side

Validation in the application layer is the first line of defence, not the only one. The database should protect itself too:

  • A separate read-only user. It should never be granted write permission.
  • Access only to views intended for exposure. Purpose-built views instead of raw tables.
  • Row-level security (RLS). Even if the application forgets the filter, the database protects the data.
  • Query timeout and resource limits. An accidental Cartesian product should not bring production down.
  • Audit log. Which user, which question, which SQL, how many rows - log all of it.

5. Handling ambiguous questions

A good Text-to-SQL system does not answer every question; it asks some back. In "How are sales this month?", it is unclear whether "this month" is the calendar month or the last 30 days, and whether "sales" means units or amount.

  • Ask a clarifying question. One short question is better than a wrong report.
  • Make assumptions visible. Show "last 30 days, by net amount, excluding returns" alongside the answer.
  • Show the generated SQL. A user who knows the data will spot a mistake within seconds; this is the cheapest validation mechanism there is.

6. Evaluation

Comparing SQL as text is misleading - two queries that return the same result can be written very differently. What needs to be measured is execution accuracy.

MetricHow
Execution accuracyWhether the generated query's result matches the reference query's result
Validity rateWhether the query runs without errors
Refusal accuracyWhether the system correctly asks back on unanswerable questions
Security violationNot a single example that goes outside the allowlist is acceptable

Build the test set from real questions and deliberately include ambiguous and unauthorised questions. What the system refuses matters as much as what it answers.

7. Production notes

  • Cache results. The same questions repeat; use the normalised question as the key.
  • Save frequently used queries. A validated query should run next time without needing to be generated again.
  • Visualise the result. A table is fine, but a single number or a simple chart is often easier to understand.
  • Monitor schema changes. When a column name changes, the context must be updated too; otherwise the system breaks silently.
  • Start small. A system that starts with three tables and ten questions earns trust much faster than one that opens up the whole data warehouse.
