1. Why RAG?

For a language model to answer a business question correctly, it needs two things: to understand language and to have access to current information belonging to that organisation. The model's weights provide the first, not the second. Company procedures change, price lists are updated, new contracts are signed; none of this is in the model's training data.

There are two options: retrain the model, or put the right documents in front of the model when it answers the question. The second is RAG (retrieval-augmented generation). In practice it is almost always the right starting point - it is cheap, when information changes you only update the index, and, most importantly, you can show where the answer came from.

The real challenge in enterprise RAG is not retrieval but authorisation

Building a demo takes a week. Taking it to production means correctly answering the question "can this user see this document?" on every query. Starting the design here is much easier than adding it later.

2. The parts of the architecture

RAG is not a single component but a pipeline. Each link can fail on its own, so you need to be able to measure each link on its own.

StageWhat it doesTypical mistake
IngestionPulls documents from source systems and converts them to textPDF/OCR losses go unnoticed
ChunkingSplits text into meaningful unitsSplitting mid-sentence, losing heading context
EmbeddingConverts chunks into vectorsUsing different models for queries and documents
IndexingStores vectors and metadataNot putting permission information into the metadata
RetrievalFinds the chunks closest to the questionRelying on vector similarity alone
RerankingOrders candidates by relevanceSkipping the step entirely
GenerationWrites the answer using the contextNot citing sources

The most insidious part of this pipeline is this: when you see a bad answer, the model usually gets the blame. Yet in most cases the problem lies in retrieval - the model cannot know information that was never put in front of it.

3. Chunking strategies

Chunking is the step whose quality is most often overlooked. Fixed-length splitting is the easiest approach but usually gives the worst results: a table's header ends up in one chunk and its rows in another.

StrategyWhenNote
Fixed length + overlapHomogeneous plain text10-20% overlap reduces loss of context
By heading hierarchyProcedures, policies, technical documentationAdd the parent headings to each chunk
Table/section awareContracts, financial statements, specificationsDo not split tables; flatten them into text if needed
Question-answer unitFAQs, support ticketsNaturally gives the highest hit rate

A practical rule: every chunk should make sense when read on its own. If you read a chunk out of context and ask "where did this come from?", the model will ask the same question.

A simple approach that carries the parent headings into each chunk:

# Başlık yolunu koruyarak bölümleri parçalara ayırır
def parcala(bolumler, maks_karakter=1200):
    for bolum in bolumler:
        onek = " > ".join(bolum.baslik_yolu)          # "İK > İzinler > Yıllık izin"
        govde = bolum.metin
        for i in range(0, len(govde), maks_karakter):
            parca = govde[i:i + maks_karakter]
            yield {
                "metin": f"[{onek}]\n{parca}",
                "kaynak": bolum.kaynak,
                "yetki_etiketleri": bolum.yetki_etiketleri,   # erişim kontrolü için
            }

4. Retrieval quality: hybrid search and reranking

Vector search captures semantic similarity but misses exact matches. When a user types a product code, clause number or abbreviation, keyword search is far more accurate. Using both together - hybrid search - is clearly better than either on its own.

  • Vector search: "how is annual leave calculated" → the relevant procedure text
  • Keyword (BM25): "clause 7.3" → the chunk containing exactly that clause
  • Fusion: combine the two lists into a single ranking (e.g. reciprocal rank fusion)
  • Reranking: score the top 50 candidates with a cross-encoder and pass the top 5 to the model
Less context beats more context

Giving the model 20 chunks does not improve the answer; irrelevant chunks distract it and increase cost and latency. After reranking, 3-6 chunks are enough for most scenarios.

5. Authorisation and data access

This is what separates enterprise RAG from a personal assistant. Two employees asking the same question should get different answers, because they have the right to see different documents.

Three rules:

  • Write permissions at indexing time. Add the access labels from each chunk's source (group, department, company, confidentiality level) as metadata.
  • Filter in the retrieval query. Fetching all chunks first and filtering afterwards is slow and moves the leakage risk into application code. The filter should be part of the vector query.
  • Reference the source system's permissions rather than copying them. Permissions change. Monitor index freshness; when a document's permissions are narrowed, trigger re-indexing. 
# Erişim sorgusunda kullanıcı bağlamı her zaman zorunlu parametre olsun
sonuclar = index.ara(
    sorgu_vektoru=gom(soru),
    filtre="sirket eq '{sirket}' and gizlilik le {seviye}".format(
        sirket=kullanici.sirket, seviye=kullanici.gizlilik_seviyesi
    ),
    ust_k=50,
)
Leaks are silent

An answer generated from an unauthorised document raises no error - it simply gives the right information to the wrong person. That is why protecting the permission filter with unit tests matters more than testing answer quality.

6. Evaluation: what to measure?

"It looked good to me" is not a metric. In RAG you need to measure at least two separate things: did you find the right document, and did the model stay faithful to the document it found?

MetricWhat it measuresHow to collect it
Recall@kWhether the right chunk is in the top k resultsTest set pairing questions with correct documents
GroundednessWhether every claim in the answer is in the contextJudge model + human review on a sample
AnswerabilityWhether the model can say "I don't know" when the information is missingDeliberately include unanswerable questions
Latency (p95)How long the user actually waitsEnd-to-end tracing, stage by stage
Cost per queryWhat happens at scaleTokens + search + reranking

Build the test set from the organisation's own questions. 50-100 real questions are worth more than thousands of synthetic ones; knowing which questions are actually asked also tells you what to improve.

7. Going to production

  • Add sources to every answer. Users should be able to open the document and verify it. This is the single feature that builds trust the most.
  • Trace stage by stage. The query, retrieved chunks, selected chunks and generated answer - all of them should be logged. When a complaint comes in, this is the only way to see which link broke.
  • Add a cache. Business questions repeat. Caching on the normalised question significantly reduces cost and latency.
  • Collect feedback. Even a simple thumbs up/down, when reviewed regularly, is the best source of improvements.
  • Monitor freshness. The question "when was this index last updated?" should have an answer on a dashboard.

8. Short checklist

  • Do chunks make sense when read on their own?
  • Are permission labels in the index, and is the filter part of the query?
  • Is there hybrid search + reranking?
  • How many chunks go to the model - more than necessary?
  • Can the model say "I don't know" when the information is missing?
  • Do answers cite sources?
  • Is there an evaluation set built from real questions?
  • Are stage-by-stage tracing and cost per query visible?

Every item on this list was chosen from issues that caused problems at least once when moving a demo to production. Going through them in order is much cheaper than a large rewrite later on.
