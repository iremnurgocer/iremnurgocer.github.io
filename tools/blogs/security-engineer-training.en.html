Warning

The test steps in this material must only be carried out in authorised or isolated lab environments. Any action performed on live systems without written permission is a criminal offence.

Foreword

This resource offers end-to-end guidance for professionals who want to become security engineers or penetration testers, from theory to practice and from ethical foundations to advanced threat modelling. Alongside understanding attack surfaces, it covers detection, defence, incident response, automation and building a sustainable security culture.

The content is based on NIST, PTES, OWASP, MITRE ATT&CK, CIS Benchmarks and Cloud Security Alliance standards. Each section explains step by step how to identify and prioritise real-world security problems, how to secure systems and how to respond during an incident. The aim is not just "breaking in", but developing specialists who can design resilient, observable and sustainable systems.

Section 1 - Introduction, Ethics and Legal Framework

Module Competencies
  • Preparing penetration testing contracts (SoW), authorisation and NDA documents.
  • Assessing pre-engagement risks and creating a test plan with rollback procedures.
  • Carrying out passive/active reconnaissance strategies in line with PTES/NIST standards.
  • Producing advanced PoCs on surfaces such as web, API, cloud and K8s, and prioritising them with CVSS plus business impact.
  • Doing detection engineering on SIEM/EDR and reporting findings to C-level & engineering teams.

1.1 Pre-Engagement Documents

Professional engagements start with documents that clarify scope, responsibilities and communication flow.

  • Statement of Work (SoW): Contains IP/URL lists, test windows, technical scope, and communication and responsibility clauses.
  • Authorization Letter: Defines authorised signatures, the test team's identity details, whitelisted IPs and emergency stop procedures.
  • Non-Disclosure Agreement (NDA): Sets out data privacy obligations, retention processes and sharing restrictions.
  • Rules of Engagement (RoE): Lists prohibited techniques, log retention methods and data handling rules.

1.2 Risk and Rollback Planning

  • Impact on live systems, downtime scenarios and business continuity plans should be assessed.
  • Snapshot/backup plans and kill-switch procedures should be set up in advance.
  • SOC/IR teams should be informed for the duration of the test, and coordination channels should be defined.

1.3 Reconnaissance

Passive OSINT

  • DNS records, certificate logs, public code repositories, public cloud asset scans.
  • Example: dig +short ANY example.com, wildcard queries via crt.sh.

Active Reconnaissance

  • nmap, masscan (lab only), httprobe, whatweb within agreed rate limits.
  • Analysis focused on service signatures, TLS certificates and API discovery (OpenAPI, Swagger).

1.4 Vulnerability Analysis

Automated scans (Burp, ZAP, Nessus) are only a starting point; manual verification and context analysis are essential. Findings in automated reports must always be triaged for false positives.

1.5 Exploitation & Post-Exploitation

  • PoCs should be "read-only" and data masking should be applied.
  • Privilege escalation or a persistent foothold should not be established without approval.
  • Every step, the tool versions used and their outputs should be provable in the report.

1.6 Reporting and Prioritisation

Findings are prioritised using CVSS v3.1 and business impact weightings. Each finding should include a summary, technical detail, PoC, remediation steps, verification and the responsible team.

1.7 Detection Engineering & SIEM Rules

  • A detection rule should be written for every critical finding (e.g. brute-force, SSRF, token abuse).
  • Rules should be analysed for false positives / false negatives and linked to a playbook.

1.8 Verification and Regression Tests

  • PoCs are run again after the fix; they are expected to fail.
  • Relevant regression tests are added to CI pipelines.
  • Audit trails and artefacts are retained.

1.9 Lab Tasks

  • Building an asset inventory and threat modelling.
  • Detecting IDOR, fixing it and writing a regression test.
  • Preparing an SSRF OOB PoC and a mitigation plan.

Section 2 - System Fundamentals, IoCs and Protection

This section covers recognising normal system behaviour, spotting indicators of compromise (IoCs) and the defensive steps to take during an incident.

2.1 Recognising "Normal" Behaviour

  • Baseline values should be established for CPU, memory and network traffic.
  • Who connects to which services should be recorded.
  • Monitoring plans should be set up with tools such as HTOP, iftop, netstat and sysmon.

2.2 Indicators of Compromise (IoC)

Layer Symptom Prevention
Network Port scans, brute-force, DDoS Firewall rate limit, fail2ban, WAF/CDN
Application SQLi, XSS, API abuse logs Input validation, WAF policies
System New users, unexpected processes Integrity monitoring (AIDE), EDR/IDS

2.3 Linux / Server Security

  • Keeping sudo access to a minimum and disabling unnecessary services.
  • Enabling tools such as Fail2ban, Wazuh and Suricata.
  • Analysing logs regularly and setting up automatic notifications.

2.4 HTTP / Web Server Defence

  • server_tokens off, security headers and TLS hardening in Apache/Nginx settings.
  • Anomaly detection at the WAF or reverse proxy layer.

2.5 Real Incident Scenarios

  • SSH brute-force: Fail2ban, IP blocking, key-based authentication.
  • SQL injection attempt: WAF rule, endpoint isolation, log review.
  • Unexpected outbound traffic: Network isolation, process analysis, IDS logs.

2.6 Incident Response Mini Playbook

Detection: Anomaly log or IDS alert.
Containment: Service isolation, firewall rule.
Analysis: Review of processes, logs and connections.
Eradication: Terminating malicious processes.
Recovery: Clean backup, applying patches.
Monitoring: Close monitoring for the next 72 hours.

2.7 Proactive Security

  • Baseline scripts, hash checks, automated patch management.
  • User awareness training, log correlation and alert thresholds.

2.8 Lab Tasks

  • Analysing normal/abnormal traffic.
  • Writing and verifying a Fail2ban rule.
  • Incident simulation and reporting.

Section 3 - Web and Application Layer Security

This section covers OWASP Top 10 focused vulnerabilities, incident detection, log analysis and defensive practices.

3.1 Application Architecture

Analyse the risks along the Client → Application Server → Database → External Services chain: XSS, CSRF, authentication, misconfiguration, injection and so on.

3.2 Common Attack Categories and Symptoms

  • SQL Injection: ' OR 1=1 patterns in logs or a rise in 500 errors.
  • XSS: Parameters containing <script>, a broken interface.
  • Broken Auth: Repeated failed logins, unexpected sessions.
  • CSRF: POST requests with missing tokens.
  • SSRF: Outbound traffic to internal IPs.

3.3 Incident Detection and Log Analysis

Identify anomalies by correlating web server logs, application logs and WAF records. Create regex or query-based alerts in the SIEM.

3.4 Secure Coding Principles

  • Input validation and an allow-list approach.
  • Context-aware output encoding.
  • Server-side authorisation checks.
  • Secure password storage (bcrypt, Argon2).
  • API security policies, CORS and rate limiting.

3.5 Defence and Tools

  • WAF (ModSecurity, Cloud WAF) rules.
  • Static analysis tools such as SonarQube and OWASP Dependency-Check.
  • Scheduled DAST scans with ZAP/Burp.

3.6 Realistic Incident Examples

  • On an SQLi attempt, temporarily disabling the endpoint and analysing the logs.
  • On an XSS alert, tightening CSP policies and verifying input encoding.
  • On authorisation breaches, revoking tokens, checking roles and strengthening the WAF.

3.7 Incident Response

  1. Detection: Alert or user report.
  2. Containment: Restrict the endpoint or user.
  3. Analysis: Log and code review.
  4. Eradication: Patch and configuration fix.
  5. Verification: Re-running the PoC should fail.
  6. Reporting: Timeline and measures taken.

3.8 Lab Tasks

  • Recording traffic and detecting attacks on OWASP Juice Shop.
  • Writing a WAF rule and observing its effect.

Section 4 - Application and API Security (In Depth)

Authentication, authorisation, input/output security, SSRF, deserialization, CORS/CSRF, rate limiting and logging in modern web and API architectures are examined in line with MITRE ATT&CK.

4.1 Architectural Foundations

Identify classes of flaws along the Client → Reverse Proxy/WAF → Application → Identity Provider → Data & External Services chain.

4.2 Authentication, Sessions and Authorisation

  • Cookie policies (HttpOnly, Secure, SameSite) and server-side session management.
  • Protection against techniques such as JWT alg none bypass and kid manipulation.
  • Password policies, MFA, brute-force rate limiting.
  • Server-side authorisation checks (preventing IDOR/BOLA).

4.3 Input/Output Security

  • Context-aware encoding, CSP and template engine hardening against XSS.
  • Parameterised queries and safe ORM APIs against SQL/NoSQL/LDAP injection.
  • Safe use of placeholders against template injection risks.

4.4 Resource Protection

Rate limiting, token bucket algorithms, idempotency keys and log correlation for abuse detection.

4.5 File Upload & Path Traversal

  • Allow-listed MIME types/extensions, AV scanning, isolated storage folders.
  • For path traversal: normalisation, chroot/jail, ID → file mapping.

4.6 SSRF

Allow-lists, egress filtering, metadata service protections (IMDSv2), blocking redirects.

4.7 Insecure Deserialization

Schema-based formats such as JSON, rejecting unknown types, using up-to-date libraries.

4.8 CORS & CSRF

  • CORS allow-list, avoiding the wildcard + credentials combination.
  • CSRF tokens, SameSite cookies, Origin/Referer validation.

4.9 Secure HTTP Headers

Enforce the HSTS, CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy and Permissions-Policy headers.

4.10 API Security

  • OAuth2/OIDC Authorization Code + PKCE, exact matching of redirect URIs.
  • Minimal scope, deny-by-default, consistent error codes and resource-level authorisation checks.

4.11 Logging & Correlation

Logs enriched with PII masking and fields such as request-id, tenant-id and latency should be combined with correlation rules in the SIEM.

4.12 Incident Response Playbook

  1. Detection → WAF/SIEM alert.
  2. Containment → Restrict the endpoint, apply a WAF rule.
  3. Collection → Logs, config, release hash.
  4. Analysis → Root cause, impact analysis.
  5. Remediation → Patch, config fix.
  6. Verification → Regression test, PoC rejected.
  7. Improvement → Automation, pipeline update.

4.13 Labs

  • Applying secure headers & CSP.
  • Rate limit rule and SIEM correlation.
  • File upload quarantine & AV scanning.
  • Testing the OAuth2/OIDC PKCE flow.

4.14 Security Gates

  • Adding SAST, SCA, DAST and secret scanning to the CI/CD pipeline.
  • Not allowing a release until it passes the "security stage".

4.15 Quick Audit Checklist

  • Cookie policies, JWT validation, IDOR checks.
  • Prepared statements, XSS protections, SSRF guards.
  • CORS/CSRF, rate limiting, logging, WAF & SIEM integration.

4.16 Review Questions

  • IR order of steps for IDOR and rate limit vulnerabilities.
  • Risks of JWT kid manipulation.
  • The difference between CSP nonce and strict-dynamic.
  • Detecting MIME spoofing.
  • Blocking SSRF at the network and application layers.
  • OAuth2 redirect URI risks.
  • Interpreting 500/401/429 correlation in the SIEM.

5.4 Web/API Testing Flow

  2. Endpoint mapping.
  3. Safe parameter validation with Repeater.

  5. Out-of-band tests (Collaborator).

5.5 Infrastructure & TLS Checks

Verification of the TLS profile, SSH security, HTTP headers and configuration.

5.6 WAF Tuning

5.7 Incident Drill

Practise containment, log collection, corrective controls and the post-mortem process with a "scan detected" scenario.

5.8 Labs

5.9 Reporting

5.10 Automation

  • SBOM generation and supply-chain checks.

5.11 Quick Checklist

  • Verify the SoW, authorisation and kill switch.
  • Make sure reconnaissance was low-noise.
  • Were WAF/SIEM correlations monitored?
  • Is the evidence masked and reproducible?

5.12 Review

Section 9 - Operational Security & Incident Response

SOC processes, SIEM, EDR, detection engineering, hunting, SOAR, playbook management and RCA.

9.1 Incident Response Lifecycle

Phase Description Tools
Preparation Plans, procedures, inventory IR plans, SIEM, SOAR
Detection Alert/anomaly detection SIEM, EDR, IDS
Containment Stopping the spread Firewall, SOAR, EDR isolate
Eradication Removing the malicious element EDR, patch
Recovery System restoration Backup, restore
Lessons Learned Process improvement Report, RCA

9.2 SOC Components

  • Tier-1 analysts, Tier-2 incident responders, Tier-3 threat hunters.
  • SOC manager and IR lead, process management and reporting.

9.3 SIEM

  • Log collection, correlation, visualisation, reporting.
  • Windows Event, syslog, firewall, WAF, VPN, CloudTrail and DNS logs.
  • The target alert time is < 2 minutes.

9.4 EDR/NDR/SOAR Integration

  • Host behaviour monitoring with EDR, network analysis with NDR, automation with SOAR.
  • EDR alert → SIEM correlation → SOAR isolation action.

9.5 Detection Engineering

  • Signature, behaviour, anomaly and hunt queries.
  • Sigma, YARA, KQL and MITRE ATT&CK-aligned rules.

9.6 Threat Hunting

  • Hypothesis-, intelligence- or behaviour-driven hunting.
  • EDR telemetry, DNS/proxy logs, CloudTrail, auth logs.
  • Hunting findings should be turned into SIEM rules.

9.7 Playbooks

  • Scenarios such as credential leaks, malicious macros and suspicious network traffic.

9.8 Incident Reporting & RCA

The summary, impact analysis, root cause, timeline, corrective actions and lessons learned should all be documented.

9.9 KPIs

  • MTTD < 4h, MTTR < 24h.
  • Alert accuracy rate > 90%, false alarm rate < 10%.
  • Playbook automation rate > 60%.

9.10 Labs

  • Creating a SIEM rule.
  • EDR alert analysis.
  • Threat hunting exercise.

9.11 Best Practices

  • Log integrity (hash & WORM storage).
  • Reducing alert fatigue, triage guides.
  • Regular tabletop exercises.
